## Operational contract
- BASELINE: ESP32 awake, 20 s sensor cadence, UART logging and local alarm; Pi continuously powered, camera and ONNX at startup then every 1800 s.
- OPTIMIZED: 20 s timer deep sleep plus awake overhead; 90 cycles (~30 min) normal, 360 (~120 min) stable. First scheduled wake at 90 cycles. After 90 consecutive valid alarm-free samples and at least one wake request, extend to 360. A newly active threshold (including another rule while one is active) or new actual sensor fault requests GPIO wake on that sample. Persistent alarms return to 90 cycles, rather than rebooting each sample. Invalid or uncalibrated readings cannot qualify as stable; missing calibration alone is not an urgent hardware fault. Existing buzzer rules and cooldown unchanged.
- Pi executes one camera/ONNX attempt per boot, flushes logs, and halts after success or a logged failed attempt so future GPIO wakes can recover. Failed cycles are not successful captures. If poweroff itself fails, the service retries within a bounded restart policy. GPIO success is not a Pi acknowledgement. A pulse while Pi is already running does not guarantee an additional image. There is no Pi-to-ESP handshake or continuous Pi logging while halted. Full sensor/policy logs must be captured via ESP USB console during functional tests.
- This policy responds to ESP sensor thresholds, not visually detectable disease; the latter can go undetected between images. Current thresholds are in esp32/config/configuration.txt. Review thresholds and physically calibrate soil before stable test; no invented calibration. Sleep duration excludes active overhead; 90/360 cycles are approximate wall-clock intervals.

## Functional test (no new energy measurement)
Record ESP UART0 console with host timestamps and save Raspberry Pi events_log.txt and test_events.csv. Keep common ground, GPIO26 to Pi GPIO3, UART and the existing EEPROM settings as in WIRING.md. Do not enable gpio-shutdown. Use a separately labelled accelerated bench build (e.g. normal 6 cycles, stable 18 cycles via menuconfig; keep sleep 20 s) and baseline CAMERA_INTERVAL_SECONDS=60 override if necessary. Do not present accelerated cadence as production timing. After testing restore 90/360 and 1800 s. Test normal wake, stable transition, immediate new alarm, persistent alarm without wake every sample, recovery, actual Pi boot/capture/inference/halt. Verify event logs and GPIO request status. Wait for actual halt before inducing a new alarm; extend accelerated intervals if boot/capture takes longer. See LAB_RUNBOOK.md. A few cycles demonstrate functionality, not six-day reliability or energy.

## Model, not measurement
Historical energy reference: BASELINE background 262.86 Wh, sensing 3.79 Wh for nominal 259200 events, camera/ONNX 7.03 Wh for nominal 8640 events; OPTIMIZED background 192.86 Wh, sensing 0.66 Wh for 25493 events. Incremental combined Pi activity estimate 55.848094 J (includes overlapping sensor events), duration ~34.72 s. See ENERGY_RESULTS.md. New baseline uses 25920 nominal sensing events and 288 nominal camera events in 144 h, so 262.86 + 3.79/10 + 7.03/30 = 263.4733 Wh. Assumes same background and linear event scaling; no direct validation. Startup/buzzer and event overlap may differ.
New optimized projection uses historical background and per-event coefficients. Count actual/modelled Pi wake activity blocks separately; report stable, normal, and alarm scenarios. Stable 120 min is ~72 nominal blocks; normal 30 min ~288 nominal blocks; actual counts depend on overhead and alarms. At the historical overhead assumption, 25,493 samples with the first request at cycle 90 then every 360 yield 71 scheduled requests (plus a possible initial Pi boot). These are not confirmed activity blocks. The first normal check and startup change counts. Use projection script with explicit counts. Subtract estimated sensing overlap within Pi blocks if counting all sensing independently (approximation); do not count wake requests as successful Pi activity without corroborating logs. No new energy numbers may be described as measured. Failed/retried activity blocks can differ from historical coefficients and must be reported separately.
